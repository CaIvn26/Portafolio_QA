E-Commerce Checkout Flow
Simulated retail web app — end-to-end purchase validation
Functional UI Validation Edge Cases Manual
Objective & Scope

Validate the complete checkout flow of a simulated e-commerce platform — from adding items to cart through payment confirmation — covering happy paths, error states, field validation, and boundary conditions. Out of scope: payment gateway internals, mobile native app.

Test Cases (representative sample)
ID Description Type Result
TC-001 Add single in-stock item to cart and complete purchase with valid credit card Positive PASS
TC-002 Apply valid 20% discount coupon before checkout — verify price calculation Positive PASS
TC-003 Attempt checkout with expired credit card (MM/YY in the past) Negative PASS
TC-004 Submit empty required shipping fields — verify inline error messages Negative FAIL
TC-005 Add quantity 0 or negative value via manual URL parameter manipulation Edge Case FAIL
TC-006 Apply two discount coupons simultaneously — verify only one is applied Edge Case FAIL
TC-007 Complete purchase with minimum cart total (1 item, $0.01) Boundary PASS
TC-008 Attempt purchase of out-of-stock item that went out of stock mid-session Edge Case FAIL
// visual Add screenshot of TC-004 showing missing error state, and a screen recording GIF of TC-006 demonstrating the double-coupon bug. Place below this table.
Bugs Found
  • HIGH Dual coupon stacking: Applying two promo codes in sequence results in both being applied, allowing orders at negative total. No server-side coupon uniqueness check. Reproducible 100%.
  • HIGH Negative quantity via URL: Manually setting ?qty=-3 adds negative quantities to cart and reduces total price. No server-side quantity validation.
  • MED Missing field error messages: Submitting checkout with empty "Shipping Address" fields shows no inline validation — form silently fails with no user feedback.
  • MED Stale stock state: Item added to cart while in stock can still complete purchase after going out-of-stock mid-session. No real-time stock revalidation at checkout.
Tools Used
Chrome DevTools Google Sheets (test tracking) Jira (bug reports) Manual Testing Loom (recording)
Value Delivered

Identified 2 high-severity business logic flaws (coupon stacking, negative quantity) that could directly result in financial loss if deployed. Documented all 4 bugs with steps to reproduce, expected vs actual results, and severity justification — ready for developer handoff. Test coverage: 8 cases across positive, negative, edge, and boundary categories.

// PROJECT 02
REST API — User Auth & Task Management
Simulated task management backend — Postman API validation
API Testing Auth Validation Status Codes Postman
Objective & Scope

Validate the REST API of a simulated task management application — covering user registration, login/logout, JWT authentication, and full CRUD operations on task resources. Focused on authentication flow integrity, proper HTTP status codes, error handling, and response body structure. Out of scope: performance/load testing, third-party integrations.

Endpoints Tested
POST /auth/register POST /auth/login GET /tasks POST /tasks PUT /tasks/:id DELETE /tasks/:id
Test Cases (representative sample)
ID Description Type Expected Result
API-001 Register new user with valid email and strong password Positive 201 + token PASS
API-002 Login with valid credentials — verify JWT returned Positive 200 + JWT PASS
API-003 Access GET /tasks without Authorization header Negative 401 PASS
API-004 Access GET /tasks with expired JWT Negative 401 FAIL
API-005 Register with already-registered email address Negative 409 Conflict FAIL
API-006 Create task with empty "title" field (required) Negative 400 + error msg PASS
API-007 Delete task belonging to a different authenticated user (IDOR check) Security 403 Forbidden FAIL
API-008 Send malformed JSON body to POST /tasks Edge Case 400 PASS
API-009 GET /tasks/:id with non-existent task ID Negative 404 PASS
// visual Add Postman screenshot showing API-007 response (expected 403, received 200). Include the response JSON body. Export and embed the Postman collection link below this table.
Bugs Found
  • CRITICAL IDOR — Broken Object Level Authorization: Authenticated User B can delete tasks created by User A by knowing the task ID. API returns 200 instead of 403. No ownership validation on DELETE /tasks/:id.
  • HIGH Expired JWT accepted: Requests with a manually expired JWT (exp set in the past) return 200 and valid data. JWT expiry is not validated server-side.
  • MED Duplicate registration returns 200: Attempting to register with an already-used email returns 200 OK instead of 409 Conflict. A duplicate user is silently created with a different internal ID.
  • LOW Error response not standardized: Different endpoints return different error body shapes — some use {error: "..."}, others use {message: "..."}. Inconsistent contract for frontend consumers.
Tools Used
Postman JWT.io (token inspection) Postman Collections Jira (bug reports) Manual Testing
Value Delivered

Caught a critical IDOR vulnerability that would expose all users' data to any authenticated attacker — a security finding, not just a functional bug. Identified that JWT expiry is entirely bypassed, making session management non-functional. All bugs include HTTP request/response evidence, reproducibility steps, and OWASP reference where applicable.
